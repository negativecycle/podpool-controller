What a PodPool is

Spot instances are dramatically cheaper than on-demand ones and can be reclaimed at a few minutes’ notice — every cloud sets its own discount and its own warning, and neither is a number this document needs. The obvious way to exploit them is to run part of your fleet there, and a Deployment cannot: it has exactly one pod template, so one nodeSelector, one priority class, one set of tolerations. Every pod it manages is identical. There is no way to say three of these on reliable hardware and the rest wherever is cheap.

So teams hand-roll it — several near-identical Deployments, an HPA on each, and a spreadsheet-in-your-head relationship between their replica counts. Scale up and you have to adjust all of them in the right proportion. Scale down and you have to remember which one holds the guaranteed floor.

Groups are ordered, earlier means filled first, and every group is the same triple: a floor, a best-effort target, and a ceiling. The floor is always min, defaulting to zero. backgroundthe restaurant, if that has not landed yet

You run a restaurant. Tonight you need ten cooks, and you have three ways to get them. Full-time staff are expensive but always show up, and you need at least three on every shift. Discount contractors are cheaper and work in your kitchen, but you send them home first when things get tight — never more than 30% of the floor. Temp agency workers are cheapest by far, but the agency can recall them with two minutes’ notice, so never more than half.

Somebody has to do the arithmetic: given I need ten tonight, how many of each do I call in? And when the dinner rush pushes that to thirty, redo it — without ever dropping below three full-timers. PodPool is that manager. You hand it one number and the rules; it works out the split.

Now swap the words. Cooks are pods. Full-time staff are pods on on-demand nodes, expensive and never taken away. Temp workers are pods on spot instances, a fraction of the price but reclaimable at any moment. Discount contractors are low-priority pods that share the reliable nodes and get evicted the instant something more important needs the room.

The manager does not interview cooks. They phone three agencies and say send three, send three, send four, and each agency handles its own paperwork and its own sick days. PodPool works the same way: it never creates a pod. It creates one child workload per group — a Deployment, a StatefulSet, an Argo Rollout, whatever the template names — and sets a replica count on each. The workload controllers do the actual pod management, which is why this is sometimes called a controller of controllers.

backgroundhow a controller thinks, if this is your first one

A Kubernetes controller is a thermostat, not a script. A script says turn the heat on. A thermostat says the target is 20°, look at the room, act on the difference. It re-reads the room constantly and never remembers what it did last time.

In Kubernetes, controllers are control loops that watch the state of your cluster, then make or request changes where needed.

00.4Trim the scaffold's CI triggers, cache the toolchain, pin kind

The scaffold declares on: push: with no branch filter alongside on: pull_request:, so every branch push runs the whole suite and opening the PR runs it again — six runs per milestone, three of them redundant.

Worse is what each run spends its time on. Every job calls a make target, every make target calls go-install-tool, and that compiles golangci-lint from source whenever bin/ is empty — which it always is, because nothing caches it. Measured here: linting takes 0.8s warm and 21s cold, while the CI job averages 5.6 minutes. The remaining five minutes are construction, repeated on every push. So: pull_request alone, a concurrency group that cancels the run a force-push superseded, and a cache over bin/ keyed on a hash of the Makefile — which is where every tool version is pinned, so a bumped pin can never restore a stale binary.

The fourth change is a pin rather than a saving. The scaffold's e2e workflow fetches kind from the unversioned dl/latest URL, so it runs against whatever released most recently — the exact drift this repository refuses everywhere else, where kwokctl is pinned and a test asserts it. An unpinned dependency in the e2e path fails a milestone's CI for reasons that have nothing to do with the commit under review.

Several of this document's strongest claims — that a check is defensive, that one test carries a whole behaviour — are results of doing this rather than assertions about the code.
